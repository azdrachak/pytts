# pytts: дизайн локального CLI для озвучивания статей

Дата: 2026-07-19  
Статус: утверждено пользователем

## 1. Назначение

`pytts` — локальное CLI-приложение для macOS на Apple Silicon. Оно принимает
русскоязычную статью в текстовом PDF или Markdown и создаёт один MP3-файл с
озвученным основным текстом. Основной сценарий — слушать статьи, сохранённые из
веб-браузера, а не обрабатывать книги.

Приложение работает на CPU. Модель Silero скачивается при первом запуске, после
чего конвертация выполняется без сети. Исходные документы и извлечённый текст не
передаются внешним сервисам.

## 2. Границы MVP

В MVP входят:

- один входной файл `.pdf` или `.md` за запуск;
- только русский язык;
- PDF с существующим текстовым слоем;
- статьи длительностью до одного часа итогового аудио;
- очистка текста статьи от технического шума;
- пользовательский YAML-словарь сокращений;
- выбор голоса и дискретного темпа;
- один монофонический MP3-файл;
- отображение прогресса и понятные ошибки.

До реализации основного конвейера обязателен интеграционный Phase 0 для
фактической проверки контракта `v5_5_ru`. Его критерии описаны в разделе 10.

В MVP не входят:

- OCR и сканированные PDF;
- книги, EPUB и другие форматы;
- пакетная обработка каталогов;
- автоматическое определение языка;
- контекстное или морфологическое раскрытие сокращений;
- преобразование чисел, дат, валют, процентов и диапазонов в слова;
- веб- или графический интерфейс;
- Docker, облачные API, GPU и `ffmpeg`;
- возобновление синтеза с последнего готового фрагмента.

Известные ограничения качества:

- числа и смешанные конструкции вроде `2026`, `15%`, `1 500 ₽` и `5–7`
  передаются модели без преобразования; произношение и падежное согласование
  зависят от Silero;
- язык не определяется автоматически; при низкой доле кириллицы приложение
  предупреждает, но не блокирует синтез;
- заголовки PDF распознаются эвристически по кеглю и могут стать обычными
  абзацами в документах с равномерным шрифтом;
- перенос регистра сокращений учитывает только первую букву, поэтому `Т.Е.`
  раскрывается как `То есть`, а не как полностью прописная фраза.

## 3. Пользовательский интерфейс

Основная форма команды:

```bash
uv run pytts [INPUT] [-o OUTPUT] [--voice VOICE] [--speed SPEED] \
  [--config PATH] [--force] [--debug] [--list-voices]
```

Примеры:

```bash
uv run pytts article.pdf
uv run pytts article.md -o article.mp3 --voice xenia --speed fast
uv run pytts article.pdf --config custom.yaml
uv run pytts --list-voices
```

Правила:

- без `-o` результат создаётся рядом с исходником с тем же базовым именем и
  расширением `.mp3`;
- итоговый файл не перезаписывается без `--force`;
- один запуск принимает ровно один входной файл, кроме режима `--list-voices`,
  в котором `INPUT` не указывается;
- поддерживаются только расширения `.pdf` и `.md` без учёта регистра;
- допустимые значения `--voice` берутся из `model.speakers` загруженной модели;
- `--list-voices` загружает модель, выводит фактический список и завершает работу;
- на свежей машине и `--list-voices`, и проверка `--voice` сначала скачивают и
  полностью загружают модель; опечатка в имени голоса обнаруживается только после
  этого;
- одновременные `INPUT` и `--list-voices` считаются ошибкой использования с
  кодом `2`, чтобы входной файл не игнорировался молча;
- если `--voice` не указан, выбирается `xenia`, когда она присутствует; иначе
  используется первый элемент `model.speakers` и выводится предупреждение;
- пустой или отсутствующий `model.speakers` считается несовместимым контрактом
  модели и приводит к ошибке модели;
- значения `--speed`: `x-slow`, `slow`, `normal`, `fast`, `x-fast`;
- темп по умолчанию — `normal`;
- `--debug` добавляет traceback и технические подробности к сообщению об ошибке.

Основной способ запуска — из checkout через `uv run`. Если команда вызывается
из другого каталога, используется форма:

```bash
uv run --project /path/to/pytts pytts /path/to/article.pdf
```

Обычный `uv tool install .` не является основным сценарием, потому что
редактируемый корневой `pytts.yaml` должен оставаться связан с приложением.

## 4. Архитектура

Система представляет собой линейный поток с изолированными компонентами:

```text
CLI
  -> InputReader
  -> ArticleCleaner
  -> AbbreviationExpander
  -> TextChunker
  -> SileroSynthesizer
  -> Mp3Encoder
  -> атомарный OUTPUT
```

Компоненты:

- `CLI` разбирает и проверяет параметры, выбирает пути и отображает прогресс;
- `InputReader` выбирает `PDFReader` или `MarkdownReader` по расширению и
  предоставляет единый интерфейс `read(path) -> Article`;
- `PDFReader` извлекает координатные текстовые блоки из PDF;
- `MarkdownReader` преобразует Markdown-токены в речевые блоки;
- `ArticleCleaner` удаляет служебный контент и нормализует текст;
- `AbbreviationExpander` применяет буквальные замены из YAML;
- `TextChunker` сохраняет границы структуры и ограничивает размер фрагмента;
- `SileroSynthesizer` управляет моделью, голосом и SSML-темпом;
- `Mp3Encoder` потоково кодирует PCM через один экземпляр LAME;
- `ConversionPipeline` координирует компоненты и преобразует внутренние ошибки
  в стабильные ошибки CLI.

Основные внутренние сущности:

- `Article`: путь источника и упорядоченный список речевых блоков;
- `TextBlock`: тип (`heading`, `paragraph`, `list_item`, `quote`) и текст;
- `SpeechChunk`: SSML-текст и тип паузы, которая следует после фрагмента.

Компоненты взаимодействуют через эти сущности, а не через детали конкретных
библиотек. Это позволит заменить PDF-парсер, TTS-модель или MP3-кодировщик без
изменения CLI и остальных стадий.

## 5. Извлечение PDF

`PDFReader` использует `PyMuPDF` и `page.get_text("dict", sort=True)`, чтобы
получить координаты блоков и размеры шрифтов. Это соответствует целевым
одноколоночным PDF, созданным через браузерную печать. Сложная многоколоночная
вёрстка может быть прочитана в неверном порядке и не поддерживается как
гарантированный сценарий MVP.

Обработка PDF:

1. Документ открывается без изменения исходного файла.
2. Зашифрованный документ без доступного текста отклоняется.
3. С каждой страницы извлекаются текстовые блоки с координатами и размерами
   шрифтов.
4. Числовые блоки в верхних или нижних 12% высоты страницы распознаются как
   номера страниц.
5. Нормализованная строка в верхних или нижних 12% считается колонтитулом, если
   совпадает минимум на двух страницах и не менее чем на половине страниц.
6. Основной размер шрифта определяется как медиана, взвешенная по числу
   символов. Короткий блок до 200 символов считается заголовком, если все его
   непустые строки набраны шрифтом не меньше 125% основного размера.
7. Блок считается пунктом списка, если начинается с маркера, тире или номера с
   точкой. Остальные блоки считаются абзацами; цитаты в PDF отдельно не
   распознаются.
8. Переносы строк внутри блока соединяются в абзацы.
9. Слово вида `сло-\nво` восстанавливается как `слово`; обычные дефисы внутри
   строки сохраняются.

Если после извлечения и очистки не осталось непустого текста, команда сообщает,
что PDF не содержит пригодного текстового слоя. OCR автоматически не запускается.
Если кегли заголовков не отличаются от основного текста, блоки остаются
абзацами; это допустимое поведение MVP, влияющее только на длину паузы.

## 6. Разбор Markdown

`MarkdownReader` использует `markdown-it-py`, а не регулярные выражения.

Сохраняются:

- заголовки;
- абзацы;
- упорядоченные и неупорядоченные списки;
- цитаты;
- видимый текст ссылок без целевого URL.

Пропускаются:

- YAML front matter самого Markdown-документа;
- изображения и их URL;
- fenced code, indented code и inline code;
- таблицы;
- определения и ссылки сносок;
- raw HTML tokens.

## 7. Общая очистка текста

`ArticleCleaner` выполняет только детерминированную локальную обработку:

- нормализует Unicode, неразрывные пробелы, пробельные символы и пустые строки;
- удаляет bare URL и служебные остатки разметки;
- сохраняет пунктуацию, числа и исходные слова;
- сохраняет границы заголовков, абзацев, пунктов списков и цитат;
- не пересказывает, не исправляет стиль и не вызывает LLM.

Пустые блоки отбрасываются. Если все блоки стали пустыми, синтез не начинается.
Числа, даты, валюты, проценты и диапазоны не нормализуются в слова.

После очистки вычисляется доля кириллических букв среди всех букв. Если букв нет
или доля кириллицы ниже 70%, CLI предупреждает, что русская модель может озвучить
текст некорректно, но продолжает обработку.

## 8. Пользовательский словарь сокращений

В корне проекта хранится редактируемый `pytts.yaml`:

```yaml
version: 1

abbreviations:
  "г-н": "господин"
  "г-жа": "госпожа"
  "ув.": "уважаемый"
  "т.е.": "то есть"
```

Порядок выбора:

1. Если указан `--config PATH`, используется только этот файл. Относительный
   путь разрешается относительно текущего рабочего каталога.
2. Иначе используется `pytts.yaml` из корня checkout — каталога с
   `pyproject.toml`, найденного относительно editable-пакета `src/pytts`, а не
   относительно текущего рабочего каталога.
3. Если корневой файл отсутствует, используется пустой словарь без ошибки.
4. Если явно указанный файл отсутствует, команда завершается ошибкой.

Схема допускает только поля `version` и `abbreviations`, требует `version: 1` и
отображение `abbreviations`, в котором ключи и значения являются непустыми
строками. Ключи, совпадающие без учёта регистра, запрещены. YAML читается через
безопасный загрузчик. Некорректный YAML, неизвестное поле, неизвестная версия или
неверный тип считаются ошибкой конфигурации до загрузки модели.

Алгоритм раскрытия:

- соответствия буквальные, а не регулярные выражения;
- более длинные ключи проверяются первыми;
- ключ не совпадает, если непосредственно слева или справа находится буква или
  цифра, то есть часть другого слова не изменяется;
- поиск не зависит от регистра;
- регистр первой буквы переносится в раскрытие: `Г-н` -> `Господин`;
- полный регистр остальных букв не переносится: `Т.Е.` -> `То есть`;
- замены выполняются одним проходом по исходному тексту, без рекурсии;
- каждому сокращению соответствует ровно одна фраза, без определения пола или
  контекста.

Раскрытие происходит после общей очистки, но до разбиения на предложения. Поэтому
точка в `ув.` удаляется вместе с сокращением и не создаёт ложную паузу.

## 9. Разбиение и паузы

`TextChunker` обрабатывает каждый структурный блок отдельно:

1. Делит блок по границам предложений.
2. Объединяет соседние предложения одного блока, пока чистый текст фрагмента не
   превысит `MAX_TEXT_CHARS`, подтверждённый интеграционным Phase 0.
3. Слишком длинное предложение делит по `;`, `:`, `,` и тире.
4. Если этого недостаточно, делит по пробелам, никогда не разрывая слово.

В Phase 0 на репрезентативном русском тексте определяется наибольшая чистая длина
`L_max`, которая успешно проходит с полной SSML-обёрткой для всех режимов темпа.
Константа задаётся как `min(800, floor(0.8 * L_max))`, то есть сохраняет минимум
20% запаса и никогда не превышает исходный кандидат в 800 Unicode-символов. Если
единственный непробельный токен длиннее итоговой константы, обработка завершается
ошибкой с указанием проблемного блока.

Каждый фрагмент оборачивается в экранированный SSML:

```xml
<speak><prosody rate="fast">Текст фрагмента.</prosody></speak>
```

Пользовательское значение `normal` отображается на SSML-значение `medium`.
Остальные значения передаются без изменения.

После закодированного фрагмента вставляется PCM-тишина:

- 120 мс между фрагментами одного абзаца;
- 350 мс после абзаца, цитаты или пункта списка;
- 700 мс после заголовка.

Эти паузы являются внутренними константами MVP и не настраиваются через CLI.

## 10. Silero и кеш модели

### 10.1. Обязательный интеграционный Phase 0

До реализации readers, cleaner и аудиоконвейера создаётся минимальный probe для
реального файла `v5_5_ru.pt`. Он обязан:

1. скачать модель по официальному URL и зафиксировать SHA-256;
2. открыть пакет через `torch.package.PackageImporter` на целевой версии Python
   и PyTorch;
3. вывести и сохранить точный `model.speakers`;
4. выполнить `apply_tts(text=...)`;
5. выполнить `apply_tts(ssml_text=...)` с `<prosody rate>` для всех пяти
   пользовательских значений темпа;
6. подтвердить mono PCM и частоты 8, 24 и 48 кГц;
7. определить `L_max` и безопасный `MAX_TEXT_CHARS` вместе с полной SSML для всех
   режимов темпа;
8. синтезировать фразу с годом, датой, процентом, суммой, валютой и диапазоном,
   после чего вручную записать наблюдаемое качество произношения.

Результат сохраняется в
`docs/superpowers/verification/2026-07-19-silero-v5_5-runtime.md`: версии Python,
PyTorch и модели, URL, SHA-256, `model.speakers`, подтверждённые сигнатуры,
размер файла модели, частоты, лимит текста и наблюдение по числам. Если любой
обязательный контракт не подтверждается, реализация основного конвейера
останавливается и дизайн пересматривается; бесшумного fallback на другой
интерфейс или модель нет.

Используется модель `v5_5_ru` с частотой 48 кГц на CPU. Официальный README на
момент дизайна перечисляет `aidar`, `baya`, `kseniya`, `xenia`, `eugene`, но
runtime-источником истины остаётся `model.speakers`. Официальный адрес модели:

```text
https://models.silero.ai/models/tts/ru/v5_5_ru.pt
```

Модель загружается standalone-механизмом `torch.package.PackageImporter`, без
`torch.hub`, клонирования GitHub и зависимости `torchaudio`.

Путь кеша вычисляется как
`Path(platformdirs.user_cache_dir("pytts")) / "models" / "v5_5_ru.pt"`. На
целевой macOS это:

```text
~/Library/Caches/pytts/models/v5_5_ru.pt
```

При отсутствии модели загрузчик:

1. скачивает файл по HTTPS во временный путь в том же каталоге;
2. показывает прогресс;
3. проверяет SHA-256 по коммитируемому package resource
   `src/pytts/model_manifest.yaml`, созданному в Phase 0;
4. проверяет, что Torch Package успешно открывается;
5. атомарно переименовывает временный файл в кешированный.

При ошибке временный файл удаляется. После успешной первой загрузки сеть для
конвертации не требуется.

Несовпадение SHA-256 не обходится автоматически. Ошибка показывает ожидаемый и
полученный хеши, URL и путь кеша, а также объясняет, что upstream-файл мог быть
перевыложен. Процесс обновления манифеста: повторно запустить Phase 0, проверить
спикеров, SSML, длину и числа, затем одновременно обновить SHA-256 и отчёт
верификации. Значения `model_id`, URL и SHA-256 в коммитируемом
`model_manifest.yaml` обязаны буквально совпадать с отчётом Phase 0. Простая
замена хеша без повторного probe запрещена.

## 11. Формирование MP3

Silero возвращает монофонический PCM с плавающей точкой. Перед кодированием
значения ограничиваются диапазоном `[-1, 1]` и преобразуются в signed 16-bit PCM.

Один экземпляр `lameenc.Encoder` используется для всех фрагментов и пауз:

- mono;
- 48 кГц;
- constant bitrate 96 Кбит/с;
- качество LAME `2`.

Это ограничивает память размером модели и одного текущего аудиофрагмента; полный
часовой waveform в памяти не накапливается.

К точному пути output добавляется суффикс `.part`: например, для `article.mp3`
запись ведётся в `article.mp3.part`. При успешном `flush()` и закрытии файла он
атомарно переименовывается в `article.mp3`. Существующий `.part` для того же
точного output удаляется при старте новой попытки. При ошибке или `Ctrl+C`
удаление `.part` выполняется по возможности, а исходный документ не изменяется.

## 12. Прогресс и ошибки

`Rich` показывает стадии:

1. проверка входа и конфига;
2. извлечение;
3. очистка и раскрытие сокращений;
4. загрузка модели, если нужна;
5. проверка `--voice` против `model.speakers`;
6. синтез с числом фрагментов, процентом и оценкой оставшегося времени;
7. финализация MP3.

Обычный режим выводит краткое сообщение без traceback. `--debug` добавляет
исходное исключение и traceback.

Коды завершения:

- `0` — успех;
- `2` — неверные аргументы CLI;
- `3` — ошибка входного файла, конфига или конфликт output;
- `4` — ошибка загрузки или открытия модели;
- `5` — ошибка синтеза или кодирования;
- `130` — прерывание пользователем.

Ранние проверки включают существование и тип входа, допустимость расширения,
output, темп и YAML-схему. Голос проверяется сразу после загрузки модели против
`model.speakers`; ошибка перечисляет фактически доступные значения. Ошибки диска
и разрешений переводятся в сообщения с конкретным путём, который не удалось
прочитать или записать.

## 13. Технологический стек

Проект использует Python 3.12, изолированный и при необходимости автоматически
скачиваемый `uv`. Системный Python 3.14 не изменяется.

Runtime-зависимости:

- `typer`;
- `rich`;
- `pymupdf`;
- `markdown-it-py`;
- `PyYAML`;
- `torch`;
- `lameenc`;
- `platformdirs`.

`torch` фиксируется точной версией в `uv.lock` для `macOS arm64` и ставится из
обычного PyPI, как рекомендует PyTorch для macOS. Отдельный CUDA/CPU index не
используется: CUDA-сборки не являются macOS wheels. Приложение явно создаёт
`torch.device("cpu")` и не зависит от `torchvision` или `torchaudio`.
Несмотря на это, PyTorch и модель остаются крупными загрузками; первая установка
и первый синтез показывают прогресс и требуют заметного места на диске.

Dev-зависимости:

- `pytest`;
- `pytest-cov`;
- `mutagen` для проверки MP3;
- `ruff`.

Структура:

```text
pyproject.toml
uv.lock
.python-version
pytts.yaml
src/pytts/
  model_manifest.yaml
tests/
docs/
```

`pyproject.toml` содержит метаданные, зависимости и entry point `pytts`.
`.python-version` фиксирует Python 3.12, а `uv.lock` — версии зависимостей.

## 15. Тестирование

Большинство автоматических тестов используют fake-синтезатор и не скачивают
Silero.

До них выполняется Phase 0 из раздела 10. Его отчёт и успешный probe являются
блокирующим условием для продолжения реализации.

Unit-тесты покрывают:

- PDF с одной и несколькими страницами;
- порядок блоков, колонтитулы, номера страниц и переносы слов;
- PDF без текстового слоя;
- Markdown с заголовками, ссылками, списками, цитатами, кодом, изображениями,
  таблицами, HTML, front matter и сносками;
- нормализацию пробелов и удаление URL;
- предупреждение при доле кириллицы ниже 70%;
- YAML-схему, отсутствующий и явно указанный конфиг;
- длинные совпадения сокращений, границы слов, регистр и одиночный проход;
- отсутствие ложного конца предложения после раскрытия `ув.`;
- обычные, длинные и экстремально длинные предложения;
- XML-экранирование и отображение `normal` -> `medium`;
- `--list-voices`, динамический список спикеров, fallback-дефолт и ошибку
  неизвестного голоса;
- выбор пауз;
- атомарную загрузку и кеширование модели через локальный HTTP fixture;
- понятную ошибку несовпадения SHA-256;
- очистку `.part` при исключении и прерывании;
- стабильные коды завершения CLI.

Интеграционный тест передаёт синусоидальный PCM реальному `lameenc`, а `mutagen`
проверяет MP3, mono, 48 кГц, bitrate и ненулевую длительность.
Тесты не требуют байтовой идентичности MP3 между разными версиями LAME; они
проверяют валидность и консистентные аудиопараметры.

Медленные ручные end-to-end проверки:

1. Первая конвертация скачивает настоящую модель.
2. Повторная конвертация проходит с отключённой сетью.
3. Репрезентативные `.md` и `.pdf` создают валидный MP3 с консистентными
   аудиопараметрами.
4. На слух подтверждаются естественные паузы и отсутствие URL, кода,
   колонтитулов и сокращений, перечисленных в активном словаре.
5. Отдельно прослушивается фраза с `2026`, датой, `15%`, `1 500 ₽` и диапазоном
   `5–7`; фактическое произношение документируется как известное поведение, а не
   гарантированное морфологическое согласование.
6. PDF с одинаковым кеглем заголовков и основного текста корректно обрабатывается,
   даже если заголовки получают паузу обычного абзаца.
7. Часовой soak-тест подтверждает, что память не растёт пропорционально длине
   итогового аудио.

## 16. Критерии готовности

MVP считается готовым, когда на целевом Apple Silicon Mac:

- `uv sync` создаёт окружение без Homebrew-зависимостей;
- Phase 0 зафиксировал SHA-256, `model.speakers`, standalone-загрузку, SSML и
  безопасный лимит реального `v5_5_ru`;
- `--list-voices` выводит тот же список, который вернула реальная модель;
- `.md` и текстовый `.pdf` создают один валидный MP3;
- голос динамически проверяется по `model.speakers`, а темп корректно выбирается
  флагом;
- изменения в корневом `pytts.yaml` влияют на следующий запуск;
- `ув.` из примера превращается в цельное `уважаемый` без ложной паузы;
- после кеширования модели повторный запуск работает без сети;
- ошибка или `Ctrl+C` не оставляют итоговый повреждённый MP3;
- автоматические тесты и `ruff` проходят;
- ручной часовой soak-тест проходит с потоковым потреблением памяти.

## 17. Возможные расширения после MVP

- локальные конфиги рядом со статьями и слои конфигурации;
- пакетная обработка;

- OCR;
- другие языки и заменяемые TTS-backends;
- коммерчески совместимая модель;
- числовое управление темпом через отдельный time-stretch backend;
- нормализация чисел, дат, валют, процентов и диапазонов;
- более строгая проверка языка;
- графический или веб-интерфейс.

Эти расширения не должны усложнять интерфейсы MVP до появления отдельного
утверждённого дизайна.
