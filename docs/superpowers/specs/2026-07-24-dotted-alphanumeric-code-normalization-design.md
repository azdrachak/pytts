# Нормализация dotted буквенно-числовых кодов: дизайн

Дата: 2026-07-24
Статус: утверждено пользователем

## 1. Контекст

`pytts` преобразует русскоязычные статьи в речь с помощью Silero. Перед
синтезом `NumericNormalizer` раскрывает числа и поддерживаемые
буквенно-числовые коды, а финальный warn-and-strip guard удаляет оставшиеся
цифры и сообщает о потере.

В статье от 2026-07-23 встретилось обозначение `V.629S`. Текущий
`NumericNormalizer` поддерживает коды вида `F-16`, `F16` и `X5`, но не
распознаёт токен с буквенными группами по обе стороны числа и точкой перед
числом. Поэтому общая латинская нормализация превращает буквы в `ви` и `эс`,
после чего guard удаляет `629`. В синтез попадает `ви.эс`, и номер рейса
теряется.

## 2. Цель

До финального guard детерминированно преобразовывать отдельный dotted-код вида
`[A-Z]{1,5}\.\d+[A-Z]{1,5}` в нейтральную речевую форму:

```text
V.629S -> ви шестьсот двадцать девять эс
AB.12CD -> эй би двенадцать си ди
```

Буквенные части читаются по английским названиям букв, числовая часть — как
русское количественное числительное. Точка служит структурным разделителем и
не произносится.

## 3. Границы

### 3.1. Входит в работу

- ASCII uppercase-префикс длиной от одной до пяти букв;
- одна литеральная точка;
- одна или более ASCII-цифр без пробелов и разделителей;
- ASCII uppercase-суффикс длиной от одной до пяти букв;
- границы целого токена;
- unit- и pipeline-тесты;
- текстовая приёмка на предоставленной статье;
- описание поддерживаемого формата в README.

### 3.2. Не входит в работу

- предметная интерпретация `V.` как слова «рейс»;
- произнесение точки как слова «точка»;
- коды без суффикса, например `V.629`;
- коды без префикса и точки, например `629S`;
- строчные или mixed-case формы;
- несколько чередующихся числовых и буквенных сегментов;
- пробелы, дефисы и другие разделители внутри нового формата;
- изменение reader, chunker, Silero, конфигурации или warning-контракта.

Точное предметное чтение нестандартной формы по-прежнему можно задать через
пользовательские `transliterations`.

## 4. Выбранный подход

В `src/pytts/text/numeric_normalizer.py` добавляется отдельное структурное
правило:

```regex
(?<!\w)(?P<prefix>[A-Z]{1,5})\.(?P<number>\d+)(?P<suffix>[A-Z]{1,5})(?!\w)
```

Замена:

1. передаёт `prefix` существующей функции `spell_code_letters`;
2. передаёт `number` существующей функции `cardinal`;
3. передаёт `suffix` существующей функции `spell_code_letters`;
4. соединяет три речевые части одиночными пробелами.

Правило выполняется до существующих `_CODE`, `_ALNUM_CODE`, `_DECIMAL` и
`_REMAINING_INTEGER`. Это гарантирует, что токен обрабатывается целиком до
общей нормализации его частей.

Новая абстракция или зависимость не вводится. Реализация остаётся в
`NumericNormalizer`, потому что использует существующие правила чтения кодовых
букв и чисел и должна выполниться до общей латинской нормализации.

## 5. Поток данных

Порядок общего конвейера не меняется:

```text
InputReader
  -> clean_article
  -> AbbreviationExpander
  -> TransliterationOverrides
  -> emoji removal
  -> NumericNormalizer
     -> dotted alphanumeric code
     -> existing numeric rules
  -> symbol normalization
  -> normalize_latin
  -> warn-and-strip guard
  -> chunk_article
  -> Silero
```

Для `V.629S` dotted-правило выдаёт полностью кириллическую строку без цифр.
Последующие этапы сохраняют её без warning.

Пользовательская `transliterations`-замена по-прежнему имеет более высокий
приоритет и может переопределить весь исходный токен до встроенного правила.

## 6. Границы совпадения и совместимость

Обе границы используют `\w`, как существующие правила кодов. Поэтому новое
правило не совпадает внутри слов и идентификаторов:

```text
preV.629S
V.629Spost
_V.629S
V.629S_
```

Эти строки сохраняют прежнее поведение и в полном произносительном конвейере
могут попасть под финальный warning.

Существующие форматы не меняются:

```text
F-16 -> эф шестнадцать
F16 -> эф шестнадцать
X5 -> икс пять
3.14 -> три целых четырнадцать сотых
V.629 -> ви.шестьсот двадцать девять
```

Повторное применение `NumericNormalizer` к результату не изменяет его:
реализация сохраняет существующий контракт идемпотентности.

## 7. Ошибки и предупреждения

Новые классы ошибок, exit-коды и warning-сообщения не добавляются.

Корректный dotted-код полностью нормализуется и не достигает warn-and-strip
guard с цифрами. Новое правило не перехватывает неподдерживаемые формы: их
компоненты проходят по существующим правилам, а оставшиеся неподдерживаемые
символы и цифры продолжают формировать warning.

Ошибки существующих `cardinal` и `spell_code_letters` сохраняют текущий
прикладной контракт.

## 8. Тестирование

### 8.1. Unit-тесты `NumericNormalizer`

Проверяются:

- `V.629S -> ви шестьсот двадцать девять эс`;
- `AB.12CD -> эй би двенадцать си ди`;
- минимальная и максимальная длина буквенных групп;
- отсутствие совпадения внутри буквенно-цифрового слова или идентификатора;
- сохранение текущего поведения неподдерживаемых `V.629`, `629S` и mixed-case
  форм без срабатывания нового dotted-правила;
- отсутствие регрессии для `F-16`, `F16`, `X5` и `3.14`;
- идемпотентность нормализованного dotted-кода.

Тест сначала добавляется в падающем состоянии, затем реализуется минимальное
правило и выполняется повторно.

### 8.2. Интеграционный тест произношения

Короткий фрагмент

```text
Судно VSL MEDKON MIRA V.629S будет перенаправлено.
```

проходит полный `PronunciationNormalizer`. Ожидания:

- результат содержит `ви шестьсот двадцать девять эс`;
- результат не содержит цифр;
- `NormalizationResult.warning` равен `None`.

### 8.3. Pipeline-тест

Pipeline с fake runtime получает Markdown-фрагмент с `V.629S`. Ожидания:

- синтезируемый chunk содержит `ви шестьсот двадцать девять эс`;
- progress events не содержат warning `Removed ... unsupported character(s)`;
- модель и writer используют существующий успешный путь без специальных веток.

### 8.4. Реальная текстовая приёмка

Предоставленный пользователем Markdown-файл не коммитится. Он проходит reader,
cleaner, abbreviations и `PronunciationNormalizer` без загрузки модели.

Ожидания для зафиксированной версии статьи:

- нормализованный текст содержит `ви шестьсот двадцать девять эс`;
- warning об удалении цифр `6`, `2` и `9` отсутствует;
- после нормализации статьи не остаётся цифр.

Финальный автоматический gate:

```bash
uv run pytest tests/text/test_numeric_normalizer.py tests/text/test_pronunciation.py tests/test_pipeline.py
uv run pytest -m "not silero"
uv run ruff check .
uv lock --check
git diff --check
```

## 9. Документация

README дополняется узким контрактом dotted-кодов:

```text
Uppercase dotted codes shaped like V.629S are read by letter names and a
cardinal number: «ви шестьсот двадцать девять эс».
```

`pytts.yaml`, зависимости и lock-файл не меняются.

## 10. Критерии готовности

Работа готова, когда:

1. Новый unit-тест проходит RED/GREEN-цикл.
2. Интеграционный и pipeline-тесты подтверждают отсутствие потери `629` и
   отсутствие соответствующего warning.
3. Существующие форматы кодов и десятичные числа не меняют поведение.
4. Реальная статья проходит текстовую приёмку без warning о `629`.
5. Полный автоматический gate проходит.
6. README описывает точную границу нового правила.
